# Game Opportunity Radar MVP 设计

## 目标

在 Luma Game Hub 内新增一个中英双语的创作者向内容/工具内页，用最低成本验证用户是否愿意为“游戏方向判断与完整机会报告”留下明确需求。

## 产品边界

- 中文路径：`/guides/game-opportunity-radar`
- 英文路径：`/en/guides/game-opportunity-radar`
- 页面性质：内容页 + 浏览器端轻量评估工具 + 付费意向入口。
- 第一版不拆独立站，不接数据库、账号系统、AI API 或支付。
- 第一版不宣称预测收入、市场规模或爆款概率；只基于用户填写的团队、预算、周期、平台和玩法复杂度，输出透明的 MVP 可交付性初筛。
- 表单数据仅保存在当前页面内，不上传服务器。

## 用户流程

1. 用户阅读页面顶部对产品价值和限制的说明。
2. 用户选择目标平台、团队规模、预算、开发周期和玩法类型。
3. 浏览器即时生成：
   - MVP 可交付性分数；
   - 推荐的首版范围；
   - 第一轮变现验证方式；
   - 最大风险与下一步应补的证据。
4. 用户可通过预填主题的邮件入口申请“完整游戏机会报告”，用于验证真实付费/咨询意向。

## 架构

- `lib/game-opportunity-radar.ts`：纯 TypeScript 类型、评分规则、范围建议和本地化输出，不依赖 React，便于单元测试。
- `components/creator/game-opportunity-radar-form.tsx`：客户端交互组件，仅负责状态和展示。
- `app/[locale]/guides/game-opportunity-radar/page.tsx`：服务端内容页、SEO 元数据、结构化数据、说明内容和 CTA。
- 更新攻略索引与 sitemap，保证中英文内链和可发现性。

## 评分原则

评分名称固定为“MVP 可交付性 / MVP delivery fit”，不是市场机会评分。分数由以下维度组成：

- 团队规模：人手越多，复杂内容的交付风险越低。
- 预算：预算越高，外包美术、测试和平台适配空间越大。
- 周期：周期越短，必须选择更小的核心循环。
- 玩法复杂度：塔防、轻量生存、模拟经营更适合小团队验证；大型 RPG/MMO 风险明显更高。
- 平台适配：浏览器、KK/Y3、Roblox、Steam 的首版要求不同，但不把平台热度或收入作为事实写入评分。

每个结果都必须同时显示“这不是收入预测”的提示。

## 内容结构

- Hero：解释“先验证做什么，再投入开发”。
- 轻量评估器。
- 大白话说明：这个产品未来卖什么。
- 三步验证框架：需求证据、可做性、付费验证。
- 数据边界与可信度说明。
- 付费报告意向 CTA。
- 指向游戏攻略索引、游戏列表和联系页的内部链接。

## SEO 与结构化数据

- 独立中英文 title、description、keywords、canonical、hreflang。
- `WebApplication`、`FAQPage` 和 `BreadcrumbList` JSON-LD。
- 加入 `/guides` 索引和 sitemap。
- 不使用虚构收入、搜索量、客户评价或平台排名。

## 验收标准

- 两个语言路径均能静态构建。
- 表单在浏览器端即时更新结果，不请求后端。
- 相同输入得到稳定、可测试的结果。
- 极端输入分数始终限制在 20–95。
- 页面明确写出“非收入预测”和数据边界。
- sitemap 和攻略索引均包含新页面。
- `pnpm test`、`pnpm type-check`、`pnpm lint`、`pnpm build` 通过；若 CI 或环境无法运行，必须明确记录。
